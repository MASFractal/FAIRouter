### Выбирает исполнителя под задачу и проверяет, что он сделал

Библиотека маршрутизации запросов между моделями, агентами и инструментами — с судьёй,
который измеряет результат, и обучением на отзывах.

## Зачем это нужно

У вас десяток моделей и агентов. Они различаются в цене в десятки раз, в скорости — в разы, а по
качеству каждый хорош в своём. Отправлять всё в самую сильную модель дорого, отправлять всё в
дешёвую — плохо. Выбирать вручную под каждую задачу невозможно.

FAIRouter выбирает исполнителя сам, а потом **проверяет результат** и учится на этом.

* **Не платить за лишнюю силу.** Метрика выбора сводит вместе прогноз качества, цену по прайсу
  исполнителя и ожидаемое время. Дешёвая модель выигрывает там, где справится.
* **Знать, что получилось.** Судья сравнивает готовый ответ с тем, что заказывали, и показывает
  расхождения по каждому пункту: заказано 4 раздела и таблица — получено 1 раздел и ноль таблиц.
* **Становиться точнее.** Отзывы копятся, веса обучаются: кандидаты сами расходятся по типам задач.

## Как это работает

Два контура, они же две петли на логотипе. Величина «качество» живёт в двух видах, и разница
между ними — сигнал обучения.

```
                    ┌──────────── РОУТЕР (до ответа) ────────────┐
   запрос ─────────▶│  признаки задачи → прогноз качества → R    │──▶ победитель
                    │  R = качество / (цена · время)             │
                    └────────────────────────────────────────────┘
                                                                        │
                    ┌──────────── СУДЬЯ (после ответа) ──────────┐      ▼
   оценка ◀─────────│  замер факта → сравнение с заказом         │◀── ответ
   отзыв  ─────────▶│  расхождения по пунктам (критик)           │
                    └────────────────────────────────────────────┘
                                       │
                                       ▼
                         обучение: контрастивное для роутера,
                         повтор оценки человека для судьи
```

**Роутер предсказывает** качество до того, как задача исполнена — по одному тексту запроса.
**Судья измеряет** качество после. Расхождение прогноза с фактом учит роутера, расхождение судьи с
оценкой человека учит судью.

## Быстрый старт

```csharp
// Модель для распознавания задачи — одна на процесс
Settings.LLM = new LLMWithOpenRouterClient(new LLMOptions
{
    ApiKey = "...",
    ModelName = "openai/gpt-4o-mini"
});

// Кандидаты: цена за миллион токенов и скорость
BaseRoutedElement[] candidates =
[
    new() { Name = "Gemini 2.5 Flash", TPS = 200, DPMTInp = 0.3, DPMTOutp = 2.5 },
    new() { Name = "Sonnet 4.6",       TPS = 60,  DPMTInp = 3,   DPMTOutp = 15 },
    new() { Name = "Opus 4.6",         TPS = 20,  DPMTInp = 15,  DPMTOutp = 75 }
];

// Ход роутинга целиком
Tracert trace = await Env.RouteAsync("Напиши обзор на 4000 знаков в научном стиле", candidates);
Console.WriteLine(trace.Winner.Name);

// Победитель ответил — измеряем и разбираем
Specifications requested = await new SpecInputService().GetSpecificationsAsync(prompt);
Specifications actual = await new SpecOutputService().GetSpecificationsAsync(answer);

Console.WriteLine(Judge.Criticize(requested, actual));
```

Отчёт критика на реальном прогоне:

```
Стиль: заказано Scientific, получено Conversational
Таблицы: заказано 1, получено 0
Ссылки на источники: заказано True, получено False
Объём в символах: заказано 4000, получено 243
Разделы: заказано 4, получено 1
...
Провалено пунктов 12 из 16
```

## Что внутри

| Возможность | Как устроено |
|---|---|
| **Выбор исполнителя** | метрика R сводит прогноз качества, цену и время; веса обмена настраиваются |
| **Разбор задания** | требования извлекаются из текста запроса одним обращением к модели, строгой схемой |
| **Замер результата** | структура считается арифметикой (объём, разделы, таблицы, код, формулы, читаемость), стиль и лексика распознаются моделью |
| **Критик** | построчный разбор расхождений между заказом и фактом — объяснимо для человека |
| **Обучение** | судья спуском по градиенту повторяет оценку человека, кандидаты разводятся контрастивно |
| **Память** | веса, ходы и отзывы в одном файле SQLite; отзыв дописывается позже хода |

Смысл распознаёт LLM, структуру считает арифметика. Маршрутизации поиском подстрок в запросе нет
нигде: исполнитель выбирается по признакам задачи, а не по совпадению слов.

## Замеры

Проект проверяется измерениями, а не на глаз — данные в [docs/research](docs/research).

**Какую модель ставить судьёй.** Семь моделей на текстах с заранее известным стилем:

| Модель | Стиль | Термины | Извлечение ТЗ | Время |
|---|---|---|---|---|
| `openai/gpt-4o-mini` | **5/5** | **1,00** | 6/6 | 8,2 с |
| `anthropic/claude-haiku-4.5` | **5/5** | 0,90 | 6/6 | 14,0 с |
| `google/gemini-2.5-flash` | 4/5 | 0,90 | 6/6 | **5,9 с** |
| `anthropic/claude-sonnet-4.5` | 4/5 | 0,90 | 6/6 | 18,5 с |
| `deepseek/deepseek-chat` | 3/5 | 0,90 | 6/6 | 11,7 с |

Извлечение требований удаётся **всем** моделям одинаково — работу делает строгая схема, а не ум
модели. Дорогая модель судьёй не лучше: `sonnet-4.5` разобрал стиль хуже `gpt-4o-mini` и вдвое
медленнее. Подробности и найденные дефекты — [judge-models.md](docs/research/judge-models.md).

Каждый замер вскрывал дефект, который не ловился ни сборкой, ни чтением кода: судья
[мерил только длину текста](docs/research/feature-scaling.md), шкала терминологии была мёртвой,
одна из моделей возвращала значение вне объявленного диапазона.

## Сборка

Нужен .NET 10 и репозиторий `AIFramework3Open`, лежащий **рядом** с `FAIRouter`: ссылки на него
относительные.

```bash
dotnet build CSharp/src/FAI.Router/FAI.Router.csproj
```

| Зависимость | Зачем |
|---|---|
| `AI` | `Vector`, `Matrix` |
| `AI.LLM` | клиент OpenRouter и structured output |
| `AI.NLP` | разбиение на предложения с учётом русских сокращений |
| `AI.NeuralNetworks` | автоград и оптимизаторы для обучения весов |
| `Microsoft.Data.Sqlite` | хранилище весов и накопленных ходов |

## Устройство

<details>
<summary><b>Метрика выбора R</b></summary>

```
        WQ·q − WC·c
R = ─────────────────
      Wt·log(t + 2)
```

`q` — прогноз качества, скалярное произведение признаков задачи на обучаемый вектор кандидата
(«на каких задачах я хорош»). `c` — стоимость запроса по ценам исполнителя. `t` — ожидаемое время.
Веса `WQ`, `WC`, `Wt` в `Settings` задают курс обмена: роутер вправе сознательно взять модель
слабее, но дешевле.

</details>

<details>
<summary><b>Спецификация — общий язык заказа и факта</b></summary>

`Specifications` описывает **и** требования к ответу, **и** свойства готового текста — один тип на
обе стороны, поэтому их можно сравнить. Стиль участвует в векторе one-hot-кодом.

Координаты приведены к соизмеримым масштабам: объёмы и счётчики логарифмической шкалой, читаемость
делением на 100, доли 0-1 как есть. Без этого объём в символах давал 97,8% нормы вектора, и судья
не отличал научный текст от детского — [измерения](docs/research/feature-scaling.md).

Масштабы заданы константами в `Specifications`. Добавили поле — добавьте и его масштаб.

</details>

<details>
<summary><b>Зачем судье обучаемая матрица</b></summary>

Заказ и факт не совпадают буквально даже при отличной работе: заказали 3000 знаков — хороший ответ
даст 2700. `TransformerW` и есть выучиваемое отображение «что просили» → «как это выглядит, когда
сделано хорошо». Единичная на старте означает наивное «факт обязан совпасть с заказом».

Обучается на оценках человека: ошибка — квадрат расхождения между косинусом судьи и «нравится /
не нравится».

</details>

<details>
<summary><b>Раскладка каталогов</b></summary>

| Каталог | Что внутри |
|---|---|
| `RoutedElements` | кандидат на исполнение: цены, скорость, обучаемый вектор соответствия |
| `JudgeLogic` | `Judge`, `Specifications`, `DiffSpec` — оценка и критика результата |
| `Services` | извлечение ТЗ и замер факта, текстовые метрики |
| `LLM` | обращения к модели: разбор запроса, распознавание стиля и лексики |
| `RotationTracking` | признаки хода, трассировка, отзыв |
| `Training` | обучение судьи и роутера, мост к тензорам автограда |
| `Persistence` | веса и накопленные ходы в SQLite |
| `Env`, `Settings` | среда соревнования кандидатов и общие настройки |

Пространство имён совпадает с каталогом.

</details>

## Состояние

Работает: полный ход роутинга, извлечение ТЗ, замер факта, критик, обучение обеих обучаемых величин,
хранилище весов и накопитель ходов с отзывами.

Ещё нет:

* журнала реальных ходов — обучение проверено на синтетике, не на живых данных;
* `Tracert.Score` никто не проставляет: связь «судья оценил ход» с трассировкой не замкнута;
* `Judge.GetSpec` не реализован, хотя `SpecOutputService` делает ровно его работу;
* `IdealMatchVector` инициализируется константой, а не по Ксавье;
* клиент модели один на процесс — судить двумя моделями одновременно нельзя.
